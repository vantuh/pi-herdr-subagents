# План: інтерактивні агенти

Портування ідей з [pi-interactive-subagents](https://github.com/amosblomqvist/pi-interactive-subagents)
(форк HazAT) у `herdr-agents`. Джерело — асинхронний tmux-плагін; ми лишаємось на Herdr
і на синхронній моделі, тому портуємо **фічі**, а не архітектуру.

Чотири фази, **кожна виконується окремо і мержиться окремо**. Наступна фаза не
починається, поки попередня не пройшла свій gate.

## Порядок і гейти

| Фаза | Що | Ризик | Залежності |
|---|---|:---:|---|
| 0 | Ліміт паралельних агентів 2–3 → 4–5 | низький | — |
| 1 | Widget статусів агентів | низький | — |
| 2 | Двонапрямлений канал (`ask_question`) | середній | фаза 1 (статус `waiting` у widget) |
| 3 | Loadout snapshot | низький | — |
| 4 | Асинхронна делегація (`wait: false` + steer-back) | високий | 1–3, рішення після фази 3 |

Фаза 3 технічно незалежна від 1–2, але стоїть після них, бо вона — передумова
фази 4, а не самостійна цінність.

## Перевірені API

Не вигадувати нові механізми — все нижче вже існує:

- `ctx.ui.setWidget(id, lines | component, { placement: "aboveEditor" })` —
  `docs/extensions.md`, приклади компонентів у `docs/tui.md`. Знімається
  передачею `undefined`.
- `pi.sendMessage({ customType, content, display, details }, { triggerTurn: true, deliverAs: "steer" })` —
  `docs/extensions.md` (`pi.sendMessage`). Потрібно лише у фазі 4.
- `pi.registerMessageRenderer(customType, …)` — кастомний рендер для власних
  `customType` повідомлень.
- Herdr `api snapshot` → стан кожного агента (`agent_status`,
  `state_change_seq`, `interactive_ready`). Уже парситься: `parseAgentSnapshot`
  (`herdr.ts`), доступ через `getAgentSnapshot` / `getSessionSnapshot`.
- Канал батько→дитина вже є: `promptAgent` (`herdr.ts`) → `herdr agent prompt`.

## Що свідомо не портуємо

- **tmux surface layer** — у нас Herdr із детермінованим 60/40 layout-ом і
  placement-локом. Форк робить `even-horizontal` після кожного spawn/exit.
- **`session-mode: fork`** — свідоме рішення: свіжий контекст замість
  форкнутої розмови (`docs/README.md`, "Known design choices").
- **Рекурсивний спавн (`subagent_agents` + `PI_SUBAGENT_ALLOWED`)** — у нас
  `HERDR_AGENT_CHILD=1` жорстко вирубає делегацію в дитині. Не змінюємо.
- **`registerToolExtension`** — рантайм-реєстрація інструментів третіми
  extension-ами. Немає споживача.

## Фаза 0 — Ліміт паралельних агентів (2–3 → 4–5)

### Поточний стан

**Ліміту в коді немає.** Ніде в extension-і не перевіряється кількість
одночасних агентів — немає ні `MAX_*` константи, ні гарди в тулзі. "2–3 max" —
це виключно текст у промптах, тобто модель може його проігнорувати, а може
й перевиконати (обмежитись двома там, де чотири доречні).

Цільове формулювання — **4–5 max**, а не жорстка п'ятірка: діапазон лишає
моделі свободу зупинитись на чотирьох, коли п'ятий агент не додає незалежної
роботи, і одночасно робить 5 легальним, а не порушенням політики.

Три місця з формулюванням:

1. `constants.ts` → `GLOBAL_INSTRUCTIONS`: *"Launch parallel `herdr_agent`
   calls only for independent reads or disjoint write slices (2–3 max)"* —
   це реально інжектиться в системний промпт Orchestrator-а.
2. `docs/README.md` → **Negative policy**: *"(2–3 agents max)"*.
3. `AGENTS.md` (плагіна) — таблиця політики делегування.

Плюс те саме є в спільних інструкціях репозиторію:
`agents/.agents/AGENTS.md` → *"keep to 2–3 agents"*. Це **не файл плагіна**, і
правило репо (`dotfiles/AGENTS.md`) прямо забороняє його правити без потреби,
бо він спільний для всіх агентів. Змінювати лише з явного дозволу
користувача — інакше плагін і глобальна політика розійдуться в цифрах.

### Що технічно вже витримує 5

- **Placement lock** (`acquirePanePlacementLock`) серіалізує спавни, тому
  5 паралельних викликів створять один правий стовпець, а не 5 конкурентних
  колонок. Кількість не має значення для коректності.
- **Rebalance** (`buildEqualAgentSplitRatios`) рахує ratio з фактичної
  кількості керованих пейнів — формула вже загальна, `1/5` виходить сама.
  Ніякого хардкоду на трьох нема.
- **State-файл** (`state.ts`) — черга на запис per-file, кількість не обмежена.

### Що тисне на верхню межу

- **Читабельність пейнів.** 5 агентів у 40% колонці = ~1/5 висоти терміналу
  кожен. На типовому 50-рядковому вікні це ~10 рядків на агента з рамкою —
  на межі корисності. Це головний реальний обмежувач, а не код, і саме тому
  верхня межа 5, а не 6+.
- **Паралельні `agent wait`.** Кожен виклик тримає власний `execHerdr`
  процес до завершення. Треба переконатись, що ліміт одночасних tool-call-ів
  Pi пропускає 5.
- **Розмір результату.** 5 артефактів по 180 рядків fallback-у в один turn
  Orchestrator-а — реальний ризик роздути контекст. Аргумент за фазу 4
  (асинхронна доставка розносить результати по turn-ах).

### Рішення

- **Жорсткого гарду в коді не робимо.** Ніякого `HERDR_AGENTS_MAX_PARALLEL`
  чи перевірки кількості в тулзі — межа лишається промпт-політикою. Причина:
  гард заблокував би легітимний випадок 6 незалежних читань, а вартість
  порушення низька (просто тісні пейни).
- **`agents/.agents/AGENTS.md` оновлено** з явного дозволу користувача, щоб
  плагін і глобальна політика не розходились у цифрах.

### Виконано

- [x] `constants.ts` → `GLOBAL_INSTRUCTIONS`: `(2–3 max)` → `(4–5 max)` плюс
      уточнення *"the limit is independence, not count — go past 2–3 only when
      every agent has genuinely independent work"*.
- [x] `docs/README.md` → **Negative policy**: `(4–5 agents max)` + причина
      верхньої межі (висота пейна в 40% колонці).
- [x] `agents/.agents/AGENTS.md` → *"keep to 4–5 agents"*.
- [x] `AGENTS.md` плагіна — цифри не містить, синхронізація не потрібна.
- [x] Smoke-тест на 5 агентів пройдено (Herdr 0.8.2, термінал 65×272).

### Результат smoke-тесту

**Стадія 1 — layout на 5 живих агентах.** `herdr api snapshot` показав рівно
одну структуру, без конкурентних колонок:

```
split_0_root   right  ratio 0.6        → Orchestrator 163 cols | колонка 109 cols
split_1_1      down   ratio 0.8        = 4/5
split_2_10     down   ratio 0.75       = 3/4
split_3_100    down   ratio 0.6666667  = 2/3
split_4_1000   down   ratio 0.5        = 1/2
```

Вкладені ratio `4/5 · 3/4 · 2/3 · 1/2` дають точні п'ятини: усі 5 пейнів
`height 13` при `y = 1, 14, 27, 40, 53`, сума 65 = повна висота табу. Усі 6
пейнів (Orchestrator + 5 агентів) в одному табі, колонка одна (`x = 192`).

**13 рядків на агента** — це і є практична межа з розділу вище. Оцінка в плані
була ~10 рядків на 50-рядковому вікні; на 65-рядковому вийшло 13. Шостий агент
дав би ~11, сьомий ~9.

**Стадія 2 — повний цикл 5 паралельних one-shot.** Усі 5 повернули
`HERDR_RESULT: status: done`. Після завершення: у табі лишився тільки
`w2V:p1X` (Orchestrator), `splits: 0`, жодного залишкового пейна,
state-файл чистий — `{"version":1,"agents":{}}`.

**Побічна знахідка (не про інфраструктуру).** Три з п'яти агентів дали
неправильні числа: `utils.ts` 181 замість 190, `agents.ts` 79 замість 87,
`schema.ts` 41 замість 37. Профіль `scout` працює на
`kiro-acp/claude-haiku-4.5`, і на точному підрахунку рядків він ненадійний.
Делегування спрацювало штатно — помилився зміст, не транспорт. Це емпіричне
підтвердження наявного правила «Orchestrator must synthesize child results,
not blindly forward them»: перевіряй числа з дитячого звіту, якщо вони
важливі для рішення.

### Gate — пройдено

П'ять паралельних one-shot агентів проходять повний цикл: спавн → рівний
layout → 5 результатів → закриття, без осиротілих пейнів і без конкурентних
колонок. Перевірено на верхній межі діапазону (5, не 4). Фаза 0 закрита.

## Фаза 1 — Widget статусів агентів

### Мета

Панель над інпутом Orchestrator-а зі станом усіх керованих агентів, щоб не
тримати в голові, хто зараз працює і як довго.

```
╭─ Herdr agents ───────────────────────── 2 running ─╮
│ 00:23  Scout — message-bus   working                │
│ 00:45  Reviewer              blocked · needs attach │
╰─────────────────────────────────────────────────────╯
```

### Дизайн

Ключова відмінність від форку: **дитина нічого не пише**. Форк тримає
activity-снапшот, який дитина оновлює сама, бо tmux не знає про стан агента.
Herdr знає — `api snapshot` уже віддає `agent_status` per-agent. Тому widget —
це чисто читаючий поллер над уже наявними даними.

Джерела:

- `listCurrentWorkspaceAgents` / `listManagedWorkspaceAgents` (`herdr.ts`) —
  які pane/tab керовані;
- `loadHerdrAgentsState` (`state.ts`) — label, профіль, lifecycle;
- `api snapshot` — `agent_status` + `interactive_ready`.

Стани для показу: `starting` (агент стартував, ще нема снапшоту), `working`,
`blocked` (Herdr віддає blocked / `agent_blocked` — підказка "attach"),
`waiting` (з'явиться у фазі 2), `idle`/`done`.

### Кого widget показує

Не всіх керованих агентів. Widget існує, щоб показувати тих, за кем ніхто
не спостерігає, а при `wait: true` оркестратор і так стоїть у тулзі, яка
рендерить `Waiting for Herdr agent <label>...` (плюс `herdr:blocked` підсвічує
пейн оркестратора в Herdr). Рядок у widget-і був би третьою копією того самого
факту, і при 4–5 паралельних синхронних викликах це 5 рядків над інпутом без
нової інформації.

Правило: **приховувати агентів, на яких оркестратор зараз блокується, крім
тих, чий статус `blocked`.**

Виняток обов'язковий. `blocked` Herdr віддає, коли дитина сидить на
approval-діалозі або питанні, а tool-call цього не розрізняє — він показує те
саме `Waiting for…` до самого таймауту. Це рівно той failure mode, під який
робився `51bd683`, і widget — єдине місце, де він видно живцем. Строгий фільтр
«тільки `wait: false`» прибрав би цей сигнал.

Реалізація — in-process `Set` labels (`awaitedAgentLabels` в `index.ts`), а не
поле в стейті: це властивість стека викликів цієї сесії, не агента, і так воно
автоматично коректне і на шляху re-wait. Блокуюче очікування має рівно дві
точки входу і два `finally`, тому пари симетричні.

`herdr:blocked` для цього **не** використовується: його payload — контракт,
який споживає власне розширення Herdr (`extensions/herdr-agent-state.ts`), тому
подія лишається незмінною.

Наслідок для поллера: порожній список видимих ≠ порожній список керованих.
Поллер зупиняється тільки коли керованих агентів нема взагалі. Якщо агенти є,
але всі приховані, тік продовжується — інакше перехід у `blocked` ніколи б не
з'явився, бо ніщо не перезапустило б поллер.

### Файли

- новий `widget.ts` — рендер рядків + мапінг `agent_status` → підпис;
- новий `runtime.ts` (або секція у `state.ts`) — зведення
  managed state + snapshot в один масив `AgentRuntimeInfo`;
- `index.ts` — таймер (1000 ms), `ctx.ui.setWidget`, знімання widget-а коли
  керованих агентів нема, cleanup інтервалу;
- новий `widget.test.ts` — рендер за фіксованим входом.

### Відхилення від початкового задуму

- **`runtime.ts` не створювався.** `listManagedWorkspaceAgents` +
  `loadHerdrAgentsState` уже дають готовий `HerdrAgentInfo[]`, тому окремий
  модуль зведення був би зайвим шаром.
- **Нове поле `startedAt` не додавалось.** У стейті вже є `updatedAt`, і тулза
  перезаписує його на кожному спавні *і* на кожному persistent-reuse — це
  точно та точка відліку, що потрібна («час у поточній задачі», не «вік
  пейна»).
- **Без рамки.** Замість box-компонента з `render(width)` — простий
  `string[]`, який `setWidget` приймає напряму. Ширина не потрібна: labels
  обрізаються до 28 символів, колонки вирівнюються між рядками.

### Верифікація

`bun test` — 84 pass / 0 fail (з них 18 нових), `bun build` збирається
(61 KB), `prettier --check *.ts` чисто.

Живий дата-шлях перевірено на **двох реальних керованих агентах** (спавн через
`herdr_agent`, `lifecycle: persistent`), семплінг `getCurrentContext` →
`listManagedWorkspaceAgents` → `renderAgentWidgetLines` раз на 3 с:

```
Herdr agents · 2 · 1 working
 00:03 Widget alpha                  working
 00:36 Widget truncation check lon…  done
```

Через кілька секунд, після завершення роботи:

```
Herdr agents · 2
 00:06 Widget alpha                  done
 00:39 Widget truncation check lon…  done
```

Підтверджено на живих даних:

- Реальні `agent_status` мапляться: `working` → активний тон + суфікс
  `· 1 working` у заголовку; `done` → тихий тон, суфікс зникає.
- Час тікає між семплами (00:13 → 00:16 → 00:19).
- **`updatedAt` дійсно перезаписується на persistent-reuse:** після повторного
  промпта в `Widget alpha` відлік скинувся з 00:36 на 00:03. Це емпірично
  підтверджує вибір `updatedAt` замість нового `startedAt` — показуємо «час у
  поточній задачі», а не вік пейна.
- Truncation і вирівнювання колонок на реальних labels.
- Після `pane close` обох агентів: `0 agents` → `renderAgentWidgetLines`
  віддає `[]` → `setWidget(id, undefined)` і поллер зупиняється. Таб
  повернувся до `panes: 1, splits: 0`.

Побічно підтверджено рішення «widget не робить prune»: закриття пейнів в обхід
плагіна лишило два мертвих записи в state-файлі, але widget показав `0 agents`,
бо `listManagedWorkspaceAgents` фільтрує по живих пейнах. Наступний
`pruneHerdrAgentsState` проти живого снапшоту прибрав обидва
(`before: 2 → after: 0`). Тобто стейл-записи не течуть у відображення і
підчищаються штатними шляхами.

Не покрито живим прогоном: `blocked` (вимагає агента на approval-діалозі) —
покритий юніт-тестом; `status` тут прямий проброс `pane.agent_status`.

### Ручна перевірка

`/reload`, спавн двох агентів, widget показує обох з тривалістю і статусом,
після закриття всіх — зникає.

Дата-шлях цього сценарію відпрацьовано (див. Верифікацію), візуальне
підтвердження в TUI отримано (див. Gate).

      `api snapshot` на тік і не пише стейт.
- [x] Візуальна перевірка в TUI — підтверджено користувачем:
      синхронний агент у панелі не з'являється (працює в правій колонці, але
      рядка нема, бо його стан друкує tool-call); при блокуючому виклику на
      єдиного керованого агента панель зникає повністю і **повертається** після
      завершення з `idle` — тобто поллер переживає порожній список видимих.

### Ризики

- Поллер плюс блокуючий `agent wait` в одному процесі — переконатись, що
  `execHerdr` з таймера не змагається з очікуванням за той самий AbortSignal.
- Тік раз на секунду × `api snapshot` — якщо дорого, підняти до 2000 ms.

## Фаза 2 — Двонапрямлений канал (`ask_question`)

### Мета

Дитина може задати батькові одне питання і **не вмерти**: сесія паркується,
батько відповідає, дитина продовжує з відповіддю. Це закриває наш найгірший
failure mode — зараз агент, що впирається в питання, дає `agent_blocked`
(див. `51bd683`), і єдиний вихід — attach руками.

### Ключова відмінність від форку

Форк робить steer у сесію батька, бо він асинхронний. **У нас це не працює**:
батько сидить всередині свого tool-call (`herdr_agent` з `wait: true`) і не
може взяти новий turn, поки тулза не повернеться. Тому:

> питання дитини завершує поточний `herdr_agent` виклик **раннім успішним
> результатом** зі статусом `question`, а не steer-ом.

Батько відповідає наступним викликом `herdr_agent` з тим самим `tabLabel` і
`task` = відповідь → `promptAgent` шле її в ту саму сесію. Дитина лишається
жива весь час. Це повне перевикористання наявного persistent-reuse шляху,
без нової транспортної магістралі до батька.

Наслідок: `lifecycle: "oneshot"` при питанні **не закриває** target — агент
лишається відкритим до фінального результату. Це вже узгоджується з правилом
"one-shot закривається лише після успішного завершення".

### Транспорт дитина→батько

Файл `question.json` у тому ж temp-наборі, що й result-файл
(`createAgentTempFiles` в `utils.ts`). Дитина пише його зі свого
child-режиму; батько поллить його під час очікування.

Батько наразі очікує серверним `herdr agent wait --until idle --until done`
(`waitForAgent`). Треба вирішити як зловити питання:

- **варіант A** — поллінг `question.json` паралельно з `agent wait`, перший
  переможець; на питанні скасувати wait;
- **варіант B** — додати `--until blocked` і після виходу перевірити файл.

Варіант A виглядає надійнішим (не залежить від того, який статус Herdr
призначить парканій сесії), але вимагає акуратного скасування. **Це open
question — уточнити перед реалізацією.**

### Файли

- `utils.ts` — `createQuestionFile`, `readAgentQuestion`, `clearAgentQuestion`;
- `constants.ts` — `CHILD_PROTOCOL`: коли можна питати (неоднозначні вимоги,
  рішення, що змінює обсяг), що робити далі, заборона питати про дрібниці;
- новий `child.ts` — виніс child-режиму з `index.ts`: result writer +
  реєстрація тулзи `ask_question`;
- `index.ts` — `ask_question` у `--tools` allowlist дитини (там, де
  `piArgs.push("--tools", agent.tools.join(","))`); гілка результату
  `status: "question"`;
- `herdr.ts` — гачок скасування очікування при питанні;
- `schema.ts` — уточнити опис `task`: він же канал відповіді на питання;
- `widget.ts` — статус `waiting · question`.

### Задачі

- [ ] Виділити child-режим у `child.ts`, зберігши поведінку result writer-а.
- [ ] Зареєструвати `ask_question` тільки при `HERDR_AGENT_CHILD=1`; параметр `question: string`, повертає підтвердження "питання надіслано, чекай наступного turn-а".
- [ ] Дитина не має завершувати turn звичайним `HERDR_RESULT` після питання — прописати це в `CHILD_PROTOCOL`.
- [ ] Додати `ask_question` до allowlist; переконатись, що профільний `tools` його не відрізає.
- [ ] Реалізувати вибраний варіант очікування (A або B) з чистими юніт-тестами на "хто переміг".
- [ ] Формат результату батькові: label, профіль, текст питання, явна інструкція відповісти `herdr_agent` з тим самим `tabLabel`.
- [ ] Не закривати one-shot target при `status: "question"`.
- [ ] Чистити `question.json` перед кожним промптом (як `clearAgentResult`) — щоб старе питання не спрацювало двічі.
- [ ] Тести: питання під час wait, питання без відповіді (target лишається), відповідь → нормальне завершення, паралельні питання від двох агентів.

### Верифікація

`bun test` + ручний сценарій: агент із свідомо неоднозначним завданням задає
питання, батько відповідає, агент завершує роботу; target закривається лише
в кінці.

### Gate

Повний цикл питання→відповідь→результат на живому агенті, без attach руками.
Жоден шлях не лишає осиротілий pane після відповіді.

### Ризики

- Дитина може спамити питаннями — обмежити одним відкритим питанням на агента.
- `--tools` allowlist: якщо Pi не пускає extension-тулзу через allowlist,
  фаза стопориться. Перевірити **першим кроком**, до всього іншого.

## Фаза 3 — Loadout snapshot

### Мета

Зафіксувати повний sandbox агента на момент спавну, щоб persistent-reuse і
майбутній resume не залежали від того, чи змінився профіль у
`~/.pi/agent/agents/*.md` між викликами.

### Дизайн

Зараз `state.ts` тримає lifecycle-стан (де pane, який label, який lifecycle),
але не **чим** агент був запущений. Якщо профіль відредагували, наступний
reuse промптить агента, який працює за старим системним промптом — а батько
думає, що за новим.

Фіксуємо в `HerdrAgentStateRecord`: `model`, `tools`, хеш системного промпту,
шлях до temp system-файлу, `cwd`.

### Файли

- `state.ts` — поля loadout у записі, версія схеми для міграції старих файлів;
- `index.ts` — писати loadout при спавні, порівнювати при reuse;
- `state.test.ts` — round-trip і читання запису без loadout (старий формат).

### Задачі

- [ ] Розширити `HerdrAgentStateRecord` полем `loadout`.
- [ ] Толерантне читання: записи без `loadout` лишаються валідними.
- [ ] При reuse порівняти поточний профіль із записаним; при розбіжності — попередити в результаті тулзи (не падати).
- [ ] Вирішити політику розбіжності: попередження чи перестворення агента. **Питання до користувача перед реалізацією.**

### Gate

`bun test` зелений, старий state-файл читається без помилок, розбіжність
профілю видно в результаті тулзи.

## Фаза 4 — Асинхронна делегація (рішення після фази 3)

### Мета

`herdr_agent` вертається одразу, Orchestrator працює далі, результат приходить
сам через `pi.sendMessage(..., { triggerTurn: true, deliverAs: "steer" })`.

### Чому останньою

Це не фіча, а зміна архітектури. Вона зачіпає весь `index.ts` і скасовує сенс
частини наявної складності:

- soft re-wait при abort/timeout (`b6ee710`) стає непотрібним — якщо не
  блокуємось, таймаут перестає бути подією;
- `wait: true` як дефолт і `oneshot ⇒ wait: true` більше не потрібні;
- закриття one-shot target-а переїжджає у фонового вотчера;
- фаза 2 спрощується: питання можна доставляти steer-ом, як у форку, замість
  раннього повернення тулзи.

Тому: спершу 1–3 (чиста цінність, малий ризик), і лише потім свідоме рішення
про 4. Можливий висновок — не робити її взагалі: блокуюча модель дає
детерміновану послідовність і простіший контроль над Orchestrator-ом.

### Ескіз (якщо йдемо)

- фоновий вотчер на агента замість `await waitForAgent` у тулзі;
- steer результату з `customType: "herdr_agent_result"` + власний рендерер;
- widget із фази 1 стає обов'язковим — інакше зникає видимість;
- `GLOBAL_INSTRUCTIONS`: результат приходить сам, не треба re-wait;
- дедуп: результат доставляється рівно раз навіть при `/reload`.

### Відкриті питання

- Що зі steer-ом, якщо Orchestrator у цей момент сам стрімить.
- Чи виживає доставка через `/reload` (вотчер живе в пам'яті extension-а).
- Чи не ламає асинхронність поточну гарантію "не дублюй делеговану роботу".

## Спільні правила для всіх фаз

- Тести: `bun test` у теці extension-а; чисті функції тестуються, I/O — ні.
- Smoke: `bun build` (команда у фазі 1) — має пройти без помилок.
- **Новий файл у пакеті вимагає `stow --restow pi` перед reload.** Stow
  симлінкує пакет `pi` **per-file**, а не директорією, тому свіжий модуль
  існує в репо, але не в `~/.pi/agent/extensions/herdr-agents/`. Pi падає з
  `Failed to load extension: Cannot find module './<new>.ts'` і **зникають усі
  інструменти плагіна** — виглядає як «тулза пропала», а не як помилка
  компіляції. Кожна наступна фаза додає новий файл, тож послідовність завжди:
  `stow -d ~/dotfiles -t ~ --restow pi` → перевірка `pi -p "reply with OK only"`
  → `/reload`.
- Перевіряти завантаження extension-а треба headless: `pi -p "reply with OK only"`
  друкує помилку завантаження в stderr. `bun build` її не ловить, бо
  `@earendil-works/*` — зовнішні host-пакети (`pi-tui` лежить вкладеним у
  `pi-coding-agent/node_modules`, окремо не встановлений).
- Після зміни симлінкованих файлів: `/reload` або рестарт Pi.
- Оновлювати `AGENTS.md` і `docs/README.md` у тому ж коміті, що змінює поведінку.
- Формат коміта як у історії плагіна: `feat(herdr-agents): …`, `fix(herdr-agents): …`.
- Prettier зі стандартними налаштуваннями (`printWidth` 80). Комміт `a4b0d7c`
  у заголовку каже «72-char», але фактично файли чисті саме за дефолтом:
  `npx prettier@3 --check *.ts`.

# План: друга хвиля портування з pi-interactive-subagents

Продовження [`plan-interactive-agents.md`](./plan-interactive-agents.md), де вже
портовано ліміт паралельних агентів, widget, `ask_question` і асинхронну
доставку. Джерело те саме —
[amosblomqvist/pi-interactive-subagents](https://github.com/amosblomqvist/pi-interactive-subagents)
(tmux-форк HazAT). Порівняння робилось по їхньому README + `activity.ts`,
`tools/safe-bash.ts`, `plugin/hooks/on-stop.sh` проти нашого
`schema.ts` / `agents.ts` / `types.ts` / спавн-блоку `index.ts` / `widget.ts`.

Правило те саме: портуємо **фічі**, не архітектуру. Кожна фаза — окремий
мерж із власним гейтом; наступна не починається, поки попередня не зелена.

## Порядок і гейти

| Фаза | Що | Ризик | Стан |
|---|---|:---:|---|
| A | Frontmatter профілю: `thinking`, `skills`, `system-prompt`, `disable-model-invocation` | низький | ✅ готово (2026-08-28) |
| B | Ізоляція дитини: `--no-extensions` + динамічний вибір `--extension` | середній | заплановано |
| C | Stall-детект за зростанням session-файлу + пінг батьку для detached | середній | заплановано |
| D | Повідомлення агенту, що вже працює (steer у живий pane) | середній | заплановано |
| E | Resume завершеної one-shot сесії через `agent_session` | середній | заплановано |
| F | Activity-деталізація widget-а з session-файлу дитини | низький | заплановано |

Порядок за співвідношенням користь/ризик, а не за цінністю: A дешева і
розблоковує решту профільних полів. C, E і F після емпіричних перевірок
(див. нижче) спираються на один спільний механізм — session-файл дитини.
У таблиці гейтів між ними лишається D: вона незалежна від session-файлу і
не повинна чекати E/F. Спільний парсер `agent_session` сідає у фазу C;
E і F його перевикористовують. Дитина нічого не пише — рішення фази 1
попереднього плану більше не порушується.

## Перевірені API

Перевірено через `pi --help`, інтроспекцію `node_modules` SDK та живі
експерименти (див. наступну секцію), нічого нового вигадувати не треба:

- CLI-флаги pi, які нам ще не використовуються: `--thinking <level>`,
  `--skill <path>`, `--no-skills`, `--system-prompt`, `--no-extensions`,
  `--extension`, `--exclude-tools`, `--session <path|id>`, `--session-id <id>`,
  `--fork`.
- Уже використовуються: `--name`, `--model`, `--tools`,
  `--append-system-prompt` (`index.ts`, збірка `piArgs`).
- **SDK (експорт `@earendil-works/pi-coding-agent`):**
  - `pi.getAllTools(): ToolInfo[]` — кожен тул несе `sourceInfo.path` і
    `sourceInfo.source`; built-in тули мають `source === "builtin"`
    (синтетичний шлях `<builtin:name>`), тули розширень — реальний шлях до
    файлу розширення. Це дає динамічну мапу тул → розширення без хардкоду
    (фаза B).
  - `DefaultPackageManager.resolve()` повертає package-aware список ресурсів,
    включно з `.pi/skills`, ancestor `.agents/skills`, configured paths і
    package skills. Його enabled skill paths передаємо у
    `loadSkills({ cwd, agentDir, skillPaths, includeDefaults: false })`, який
    повертає **`LoadSkillsResult`** (`{ skills, diagnostics }`), не голий
    `Skill[]`. У кожного `Skill` є `name` і `filePath`.
  - `ScopedModel` **не містить** source-інфо: мапа модель → розширення
    динамічно недосяжна, для провайдерів потрібен статичний список +
    безпечний fallback (фаза B).
  - `--no-extensions` вимикає **дискавері розширень**, не лише тули.
    `getAllTools()` бачить лише розширення, які вже завантажені в процесі
    оркестратора **і** зареєстрували тул. Розширення без тулів (наприклад
    `herdr-agent-state.ts`) у мапі немає — їх треба додавати явно (фаза B).
- Herdr: `agent start|prompt|wait|send-keys|read|get`, `api snapshot`,
  `pane split --cwd`, `tab create --cwd`. `parseAgentSnapshot` сьогодні читає
  лише `agent_status`, `state_change_seq`, `interactive_ready`, але реальний
  `agent get` віддає більше: **`agent_session` — об'єкт `AgentSessionInfo`**
  (`source`, `agent`, `kind`, `value`) плюс `revision`, `cwd`. `kind` —
  `id` або `path`; `value` є шляхом до файлу **лише коли `kind` === `path`**.
  Для `--session` підходять обидва; для `stat`/розміру у C/F — лише `path`.
  Це ключ до фаз C/E/F.
- Наш state-файл (`state.ts`) уже зберігає per-agent запис із `resultFile`,
  `automationName`, `lifecycle`, `updatedAt`, `detached` — місце для нових
  полів є.

## Емпіричні перевірки (2026-08-27)

Три живі експерименти в Herdr-сесії, кожен змінив дизайн фаз:

1. **`state_change_seq` тікає лише на реальних переходах стану.** Прямі
   socket-запити `pane.report_agent` до Herdr: два ідентичні звіти
   `working` → seq не рухнув; реальний перехід `working → idle` → стрибок
   `1120 → 1124`; звіт після `done` — проігноровано. Плюс у вихідному коді
   `~/.pi/agent/extensions/herdr-agent-state.ts` (встановлює Herdr):
   pi-сторона дедуплікує звіти, а `agentActive` хитається тільки на
   `agent_start`/`agent_settled` — тобто **всередині одного ходу seq замерзає
   назавжди**, скільки б тулів не виконувалось. Стал-детект «мертвий seq +
   working» з попередньої редакції цього плану дав би хибний stall на кожному
   здоровому довгому ході — дизайн фази C переписано.
2. **Session-файл — сигнал прогресу на межі ходу.** Живий one-shot агент
   (`sleep 45` в одному тулах виклику): під час усього ходу seq = `1137`
   без руху, session-файл — `0` записів; після завершення ходу всі
   `6` записів з'явились разом. У сесії оркестратора, навпаки, запис
   дописується одразу після кожного tool-result. Наслідок для C: поріг має
   бути «ход-масштабним» (десятки хвилин), бо між ходами здорової TUI-дитини
   файл не росте. Наслідок для F: live-деталізація «який тул активний прямо
   зараз» з session-файлу неможлива — лише post-factum (завершені ходи).
3. **Діти репортлять `agent_session`.** Реальний spawned-агент: `agent get`
   одразу віддає `agent_session` (`kind` + `value`). Фаза E не потребує
   `--session-id <uuid>` угадування: референс уже доступний. Імплементація
   мусить дивитись на `kind`, а не завжди трактувати `value` як шлях.

Обмеження виявлене разом із цим: TUI-дитина агломерує записи session-файлу
на межі ходу, тому session-файл дитини бідніший на події, ніж сесія
оркестратора на ту саму роботу. Керувати цим не можемо (стратегія запису —
всередині pi), тільки враховувати в порогах.

## Фаза A — Frontmatter профілю

### Мотивація

`discoverAgents` (`agents.ts`) читає лише `name`, `description`, `tools`,
`model`, body. У форку профіль керує ще й рівнем мислення, скілами та формою
системного промпту. Практична різниця: scout не має думати як reviewer, і
дитина зараз тягне **всі** скіли з диску, хоч ролі потрібні одна-дві.

### Дизайн

Розширити `AgentProfile` (`types.ts`) і парсер (`agents.ts`):

| Поле | Дія при спавні |
|---|---|
| `thinking` | `--thinking <level>`; валідувати проти `off, minimal, low, medium, high, xhigh, max`, невідоме — проігнорувати з попередженням у `details` |
| `skills` | кома-список імен → `--no-skills` + `--skill <path>` для кожного знайденого; ненайдене ім'я не валить спавн |
| `system-prompt` | `append` (дефолт, як зараз) або `replace` → `--system-prompt` замість `--append-system-prompt`. `CHILD_PROTOCOL` **завжди** додається, навіть при `replace` |
| `disable-model-invocation` | профіль лишається спавнибельним по імені, але зникає з опису `agent` у схемі/`details` |

Резолв `skills` — через SDK `DefaultPackageManager.resolve()` із тим самим
`cwd` / `agentDir`, далі enabled skill paths подаються у
`loadSkills({ ..., includeDefaults: false })`. Це охоплює user/project `.pi`,
ancestor `.agents`, configured paths і package skills із тими самими
пріоритетами, що й pi. Ім'я → `skill.filePath` → `--skill <path>`. Відсутні
configured packages при резолві не інсталюємо. Окремого кешування між
спавнами не робимо, щоб не отримати дрейф від settings або диску.

`cwd` навмисно **не** в цій фазі — див. відкриті питання.

### Тести

- unit (`agents.test.ts`): парсинг кожного поля, невалідний `thinking`,
  порожній `skills`, `system-prompt: replace` зберігається як значення
  профілю (парсер не збирає argv).
- contract (`contract.test.ts`): точний argv `agent start` для профілю з усіма
  полями; при `system-prompt: replace` у argv є `--system-prompt` **і**
  `CHILD_PROTOCOL` (це спавн-блок, не `agents.ts`); профіль без нових полів
  дає **байт-в-байт** попередній argv.

### Гейт

`bun run test` зелений; профіль без нових полів не змінює жодного аргументу.

## Фаза B — Ізоляція дитини

### Мотивація

Ми передаємо тільки `--tools`, тому в кожній дитині ініціалізуються **всі**
знайдені розширення. Їхні тули відфільтровані аллоулістом, але інжектовані
інструкції, віджети й хуки лишаються: зайвий контекст, довший старт,
неочікувані side-effect-и в автономній дитині. Форк стартує з
`--no-extensions` і повертає назад лише те, що бекає дозволені тули.

### Дизайн

Хардкод-мапи тул → розширення **не** буде: інтроспекція дає її безкоштовно
і без дрейфу.

1. При спавні з аллоулістом: `pi.getAllTools()` → для кожного дозволеного
   тула беремо його `sourceInfo`. `source === "builtin"` → нічого не треба;
   інакше `sourceInfo.path` — файл розширення, який реєструє цей тул →
   `-e <path>`. Один і той самий файл додається один раз.
2. **Провайдери моделей — головна пастка фази.** `--no-extensions` вбиває й
   розширення-провайдери: профіль `reviewer` з `model: kiro-acp/...`
   впаде без розширення `kiro-acp`. Динамічно це не вирішується
   (`ScopedModel` без source-інфо, див. перевірені API), тому:
   - статичний список `PROVIDER_EXTENSIONS: Record<providerPrefix, path>`
     у `constants.ts` (сьогодні один запис: `kiro-acp`);
   - провайдер профілю не built-in і не в списку → **не ізолюємо**: спавн без
     `--no-extensions`, як зараз, плюс попередження у `details`. Мовчазно
     зламати модель — гірше, ніж тимчасово не ізолювати.
3. **`--no-extensions` вимикає дискавері, не лише тули.** `getAllTools()`
   не бачить розширень без тулів. Без явного `-e` дитина втрачає
   `pane.report_agent` / `pane.report_agent_session` — ламається wait/idle,
   widget і весь спільний механізм C/E/F. Тому при `--no-extensions`
   **завжди** додаються (шляхи з `import.meta` / сусіднього файлу, не
   хардкод `~`):
   - `herdr-agents/index.ts` — `ask_question` і артефакт-райтер (`child.ts`).
     Тул реєструється лише в child-режимі (`HERDR_AGENT_CHILD=1`), тому в
     процесі оркестратора його запису в `getAllTools()` немає;
   - `herdr-agent-state.ts` — Herdr-репорти статусу і session path.
     Тулів немає взагалі, інтроспекція його ніколи не підхопить.
   Інші herdr-інтеграції без тулів (`zz-composer-herdr-agent.ts` тощо)
   `getAllTools()` теж не бачить. У першій ітерації їх не додаємо; якщо
   знадобиться — окремий запис у той самий always-on список, не евристика.
4. Тул з аллоулісту, якого немає в `getAllTools()` (невідоме ім'я або тул
   іншої ролі) → попередження у `details`; дитина отримує менше тулів,
   ніж обіцяв профіль, — це має бути видимим, а не мовчазним.
5. Профіль без `tools` (немає аллоуліста) лишається як зараз — повна дитина
   без `--no-extensions`. Ізоляція вмикається лише разом з обмеженням тулів
   і лише якщо провайдер моделі відомий (пункт 2).

### Тести

- contract: argv містить `--no-extensions`, `-e` для herdr-agents **і**
  `-e` для herdr-agent-state; тул, зареєстрований тестовим розширенням,
  додає його шлях; built-in тул — не додає нічого; невідомий тул →
  попередження у `details`; провайдер не в `PROVIDER_EXTENSIONS` → спавн
  без ізоляції + попередження; профіль без `tools` не отримує
  `--no-extensions`.
- e2e (`e2e/flow.test.ts`): реальна дитина з `tools: read` усе одно виконує
  `ask_question` і пише `result.md`; ізольована дитина все ще змінює
  `agent_status` і віддає `agent_session` (без `herdr-agent-state` цей
  кейс червоний — це гейт фази).

### Гейт

`bun run test:e2e` зелений — доводить, що ізольована дитина не втратила
ані `ask_question`/артефакти, ані Herdr-репорти (`agent_status`,
`agent_session`).

## Фаза C — Stall-детект

### Мотивація

Detached агент, що завис, зараз виявляється лише поглядом на widget або по
таймауту синхронного очікування. Форк має поле `interactive` і стеїрить батьку
на переходах `stalled` / `recovered`.

### Дизайн (переписано після емпіричних перевірок)

Вихідна ідея «мертвий `state_change_seq` + `working` = stall» **спростована
експериментом**: seq тікає лише на переходах стану, а pi-стороннє
розширення Herdr звітує стан тільки на межі ходу — всередині довгого
здорового ходу seq замерзає (див. «Емпіричні перевірки», п. 1).

Замість цього — зростання session-файлу дитини (залежить від фази B:
ізольована дитина мусить і далі вантажити `herdr-agent-state.ts`):

- `parseAgentSnapshot` (`herdr.ts`) розширюється полем `agent_session`
  (`kind` + `value`). Для `stat`/розміру беремо `value` лише коли `kind`
  означає path; `kind: id` → stall-детект мовчить (немає файлу);
- у state-запис: `sessionFile` (path, якщо є), `sessionRef` (`kind`+`value`
  для resume), `lastFileSize`, `lastGrowthAt`;
- статус `stalled`, якщо `agent_status === "working"`, а session-файл не
  зростав понад `HERDR_AGENTS_STALL_MS` (дефолт піднятий до ~15 хвилин:
  дитина дописує записи пакетно на межі ходу, тому здоровий хід із одним
  довгим bash-тулом теж дає паузу в зростанні). Це **таймаут ходу**, не
  детектор hang всередині тула;
- `stalled` показується у widget-і тоном `attention` (як `blocked`);
- **один** steer батьку на вхід у `stalled` і один на `recovered`, лише для
  `detached` агентів. Прапорець `stallNotified` у записі, щоб не спамити;
  скидається на `recovered` (будь-яке зростання файлу або зміна статусу).

Файл відсутній або `stat` кидає ENOENT/EACCES → stall-детект мовчить:
це діагностика, а не коректність. Порожній **існуючий** файл (size 0) —
не «відсутній»: годинник іде, stall може спрацювати. Мовчання лише на
помилці доступу, не на нульовому розмірі.

Синхронний шлях пінгів не отримує: там оркестратор і так стоїть у тулі й має
свій `timeoutMs`.

### Тести

- unit (`widget.test.ts`): `stalled` рендериться, тон правильний.
- integration: `neverSettle` + файл, що не росте, + перемотаний час →
  рівно один steer, потім зростання файлу → `recovered` → рівно один;
  відсутній session-файл (ENOENT) → steer-ів немає; порожній існуючий
  файл + перемотаний час → stall як для «не росте»; `kind: id` без path →
  steer-ів немає; персистентний не-detached агент steer-ів не дає.

### Ризик

Хибнопозитивні спрацювання на дуже довгих одиночних тулах (build, e2e).
При пакетному записі «файл не ріс 15 хв при `working`» ≈ таймаут ходу, не
hang. Це невиправне без live-сигналу від дитини (писати його — порушення
рішення фази 1 попереднього плану, див. F). Тому дефолт ~15 хвилин,
`attention`-тон, один steer без повторів. Якщо шум — підняти поріг, не
міняти логіку.

## Фаза D — Повідомлення працюючому агенту

### Мотивація

Єдиний спосіб додати дитині контекст зараз — дочекатись `idle` або її
`ask_question`. Якщо на середині роботи стало ясно, що вона копає не туди,
зробити нічого не можна. Форк друкує повідомлення в живий pane і дитина
підхоплює його на межі ходу; `herdr agent send-keys` у нас уже є (вживається
для Enter-nudge).

### Дизайн

Окремий тул `herdr_agent_message` — **не** новий режим `herdr_agent`. Причина:
`herdr_agent` тримає весь життєвий цикл (спавн, аллоуліст, layout, закриття), і
додавання туди «а ще іноді просто надрукуй текст» ламає його контракт і тести.

```ts
{ tabLabel: string; message: string }
```

Поведінка:

- цільовий агент шукається серед керованих по точному label (та сама функція,
  що і для reuse);
- `working` → `agent send-keys` із flatten-ом переводів рядка + Enter, повернути
  «доставлено, підхопиться на межі ходу», **не** чекати;
- `idle` / `done` → відмовити з підказкою «використай `herdr_agent` з тим самим
  `tabLabel`», щоб не було двох шляхів до однієї дії;
- нічого не змінює у state-записі, крім `updatedAt`.

Свідомо не робимо: доставку результату після такого повідомлення. Хто чекав —
чекає далі; хто detached — отримає через поллер.

### Тести

- integration: steer у `working` агента → `send-keys` argv з flatten-ом;
  `idle` → помилка з підказкою; невідомий label → помилка зі списком відомих.
- e2e: реальна дитина отримує друге повідомлення посеред ходу і згадує його в
  фінальному результаті.

## Фаза E — Resume завершеної сесії

### Мотивація

One-shot pane закривається, контекст дитини втрачається, лишається `result.md`.
Форк тримає registry `name → session file` і резюмить завершену сесію новим
повідомленням. Рішення прийнято: робимо.

### Дизайн

`--session-id <uuid>` з попередньої редакції **не потрібен**: Herdr сам
звітує `agent_session` (`kind` + `value`, див. «Емпіричні перевірки», п. 3).
`--session` приймає і path, і id. Парсер — той самий, що у фазі C.
Порядок:

1. Після старту, при першому успішному `agent get` (спавн-блок уже робить
   перевірку стану), зчитуємо `agent_session` у `sessionRef`; якщо `kind`
   — path, дублюємо `value` в `sessionFile`. Зберігаємо **базовий** `piArgs`
   **без** `--session`: інакше другий resume допише прапорець двічі.
2. При закритті one-shot запис **не видаляється**, а помічається
   `closed: true, closedAt`. Temp dir / `resultFile` прибираються як зараз
   (oneshot cleanup) — session-файл живе в `~/.pi/agent/sessions/`, не в
   tmpdir, тож cleanup артефакту resume не ламає.
3. **Retention — обов'язкова зміна pruning-у.** Тепер `pruneHerdrAgentsState`
   знищує запис будь-якого не-живого pane на кожному тику поллера (~1 с),
   тож без carve-out закритий one-shot зникне раніше, ніж його хтось
   презюмане. Нове правило: `closed`-записи тримаємо `HERDR_AGENTS_RESUME_TTL`
   (дефолт 7 днів), живі — пруняться як зараз.
4. `herdr_agent` з `tabLabel` закритого агента і новим `task` → новий pane,
   базовий argv + один `--session <sessionRef.value>`, той самий label;
   запис мігрує на новий terminal-ключ, `closed` скидається. Якщо
   `kind` був path і файлу вже немає (стерли раніше за TTL) — відмова
   з явною помилкою, `closed`-запис пруниться; мовчазний fresh spawn
   під тим самим label заборонений.
5. Конфлікт label-ів: label закритого збігається з живим → пріоритет у
   живого (reuse як зараз), закритий чекає свого TTL.

### Обмеження

- Resume повертає в контекст і старі tool-результати, і старі помилки —
  плата за продовження замість fresh session. Тому «fresh context» з
  `docs/README.md` лишається дефолтом: resume — лише через явний `tabLabel`
  закритого агента, не через `agent`-ім'я.
- `--fork` замість `--session` («продовжити без ризику зіпсувати оригінал»)
  лишається поза першою ітерацією — споживача не видно.

### Тести

- integration: закриття one-shot → запис живе з `closed: true`; TTL минає →
  запис пруниться; `herdr_agent` з label закритого + `task` → argv містить
  рівно один `--session <value>` (і після другого resume теж один);
  session-файл стерто → явна помилка, не fresh spawn; label-конфлікт →
  пріоритет живого.
- e2e: повний цикл — one-shot виконується, закривається, resume тим самим
  label → нова відповідь враховує контекст першої задачі.

## Фаза F — Activity-деталізація widget-а

### Мотивація і чому це вже не перегляд рішення

Фаза 1 попереднього плану явно вирішила: «дитина нічого не пише», бо Herdr
вже віддає `agent_status`. Це лишається правильним для **статусу**.
Попередня редакція цього плану збиралась порушити це заради live
`active · bash 7m` через `activity.json` від дитини. Емпіричні перевірки
відкрили інший шлях: session-файл дитини вже містить **завершені** ходи
й тули, і Herdr віддає референс (`agent_session`). Це **даунгрейд** відносно
форку / старої F, не еквівалент: під час ходу файл не росте, тож «last»
і «7m ago» — з **попереднього** ходу. Live-тул недосяжний без порушення
рішення фази 1. Widget показує post-factum деталізацію, не поточний тул.

### Дизайн

- `parseAgentSnapshot` віддає `agent_session` (`kind` + `value`) — спільна
  зміна з фазою C; деталізація лише коли `kind` дає path;
- поллер читає хвіст session-файлу (останні ~64 КБ, раз на тик — дешево)
  як JSONL: рахуємо записи за `type` (ходи / tool-call), не рядки.
  Великий tool-result легко витіснить історію з 64 КБ — тоді показуємо
  те, що видно в хвості, без претензії на повний рахунок;
- widget під час `working` показує post-factum на кшталт
  `working · 3 turns · last: bash · 7m ago` (останній **завершений** хід);
  файл відсутній/порожній/`kind: id` → рядок точно як зараз;
- Herdr лишається джерелом істини для статусу; session-файл — лише
  деталізація. Дитина не пише нічого — рішення фази 1 зберігається.

### Гейт

Видалення/недоступність session-файлу не змінює нічого, крім деталізації
рядка — це перевіряється тестом, а не оком.

## Що не портуємо

Додатково до списку в `plan-interactive-agents.md`:

- **`safe_bash` (блок-лист деструктивних команд для дітей)** — обгортка
  блокує ~десяток патернів (`rm -rf /`, `sudo`, `curl|sh`...), але обходиться
  одним `node -e` чи `base64 | sh`: це не sandbox і не модель безпеки, а
  ілюзія захисту. Дитина й так має канал `ask_question` для сумнівних дій,
  а проти очевидної катастрофи дешевший захист — абзац у `CHILD_PROTOCOL`.
  Повертатися до цього тільки якщо з'явиться реальний інцидент або legit
  sandbox-механізм.

- **Рекурсивний спавн** (`subagent_agents` + `PI_SUBAGENT_ALLOWED`) — рішення
  лишається: `HERDR_AGENT_CHILD=1` вирубає делегацію в дитині. Якщо колись
  переглядати, то саме whitelist-моделлю форку (список дозволених цілей у
  профілі, який і видає тулсет спавну), а не зняттям прапорця.
- **`cli: claude`** + Stop-хук із sentinel-файлом — цікаво як шаблон
  гетерогенних бекендів, споживача немає.
- **`auto-exit` як рішення дитини** — у нас закриття one-shot робить
  оркестратор після зібраного результату; це детерміністичніше. Разом з тим
  форк покриває кейс «людина щось дописала в pane руками», якого в нас немає в
  описі поведінки — записати як відомий пробіл, не як фазу.
- **`PI_SUBAGENT_SHELL_READY_DELAY_MS`** — ми стартуємо через
  `herdr agent start`, а не друком у шелл.
- **Авто-суфікси імен** — уже є (`uniqueLabel`, і в pane-, і в tab-режимі).
- **`config.json` у теці розширення** — конфіг тримаємо в env
  (`HERDR_AGENTS_LAYOUT`), другого механізму не додаємо.

## Відкриті питання

1. **`cwd` / role folders.** Форк дає ролі власну теку з власним AGENTS.md і
   `.pi/`. У нас `cwd` є в `HerdrAgentInfo`, але pane завжди успадковує cwd
   оркестратора. Питання не в реалізації (`pane split --cwd` уже вміє), а в
   тому, чи додавати `cwd` у схему тула — ми навмисно тримаємо її вузькою
   (layout, наприклад, з неї прибраний). Пропозиція: спершу тільки
   `cwd:` у frontmatter профілю, у схему не додавати.
2. **Per-call override моделі.** Форк має `model` у виклику. Наша схема — ні, і
   поки що це радше плюс: вибір моделі належить ролі. Не робити без реального
   кейсу.
3. **Поріг stall-у.** Дефолт ~15 хвилин — вгадане число, і воно нижче
   стелі через пакетне дописування session-файлу на межі ходу. Уточнити
   після першого тижня з фазою C; паралельно перевірити на реальних
   довгих ходах (build, e2e), чи не з'являється дрібніший сигнал зростання
   (думки/стрімінг дописуються раніше за tool-result). Якщо з'являється —
   поріг можна знижувати.
4. **Джерело `agent_session` для дітей із нестандартним CLI.** Якщо колись
   з'явиться дитина, що стартує не через TUI-pi (фаза «гетерогенні
   бекенди» з форку), `agent_session` для неї не гарантований — фази C/E/F
   мусять деградувати мовчки, як і описано в їх гейтах.
